# Agent Note: Runtime identity and clock context

Status: implemented

## Problem

用户问“今天是几号”“现在几点”时，链路没有提供一致的时钟来源。ReAct 提示词虽然已经渲染本地时间，但 hybrid 与闲聊路径没有等价上下文。身份回答也不稳定：底层模型可能把“你是谁”答成自己的产品名和厂商名，而不是 Artoo。能力问答存在同样的问题：模型可能罗列通用 LLM 能力，而不是描述 Artoo 当前可用的数据源和工具。

## Decision

所有聊天生成路径现在使用共享的运行时上下文契约：

- Artoo 是产品身份。提示词要求用简洁、友好的方式介绍 Artoo 的角色，并禁止主动透出底层模型、供应商或版本。
- 能力问答必须基于当前运行时上下文和可用工具，而不是按通用聊天模型作答；不得承诺不可用的动作。
- 服务端渲染可作权威依据的日期/时间，并解析调用方时区。
- 浏览器在聊天请求中发送可选 IANA 字段 `timezone_name`；缺省或非法值回退到服务端本地时间。
- Agent 提示词接收同一份时区感知上下文；非 Agent 提示词以共享 runtime block 作为基础系统提示词。

## Alternatives considered

**用关键词规则识别时间问题，并返回服务端生成的固定文本。** 已否决，因为改写、多语言和混合时间/日期意图会让规则很脆弱；绕过 Agent 后也无法保持 ReAct 人设和回答格式行为。

**只在 ReAct 提示词里继续保留当前时间，并单独加一条身份指令。** 已否决，因为 hybrid 和闲聊请求仍然缺少这两项保证，provider 身份泄露问题在快速问答和闲聊路径上无法解决。

## Consequences

前端和 Open API 新增可选字段 `timezone_name`。由于字段可选，既有客户端仍然有效。每个生成回合会增加一小段身份和时间提示词。底层模型的预训练倾向无法靠提示词在所有情况下绝对约束，因此这是行为契约和护栏，不是加密级的披露控制。非法的客户端时区字符串不会回显进提示词。

## Testing

基于 `backend/.venv` 的聚焦后端测试覆盖时区感知运行时上下文、非法时区回退、Artoo 自我介绍和能力契约、Agent 提示词契约，以及非 Agent 消息构建。前端 `npm run build` 验证请求负载和 TypeScript 契约。
